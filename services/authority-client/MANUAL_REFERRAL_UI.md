# Manual referral application transfer

The independent staging Referral Intake route connects the existing-patient manual creation and confirmation states to the already reviewed S3 transaction implementation. It preserves explicit patient selection, priority, separate new and ready_for_admission states, immutable request retries and reopening by scoped URL. No document processing, new Patient creation, admission, assignment, external messaging or general referral edits are enabled.

The strict signed-session client admits s3_create, s3_confirm, s3_read, s3_list and dedicated referral_patient/referral_patients reads. It validates exact fields, request/result identities, current intake-role context, revisions, provenance and workflow transitions, and snapshots nested request fields before dispatch. The existing SDK session/tenant membrane encloses the adapter calls. Preparation independently reads the selected synthetic patient and requires the selected membership revision to match. No role or customer identity is inferred from a patient name.

An uncertain write retains its original request/body in component memory and locks the creation fields. Retrying reuses that exact request. Navigation or reload does not persist an uncertain draft; the interface explicitly asks staff to keep that page open. This is a synthetic staging acceptance limitation, not a complete production recovery implementation. Reopened confirmed referrals do not offer a second confirmation. Clinical/provider release controls remain disabled; production still selects the original application.

The real-Auth compiled browser journey creates and confirms one referral for each agency administrator, then repeats creation/confirmation/reopening as manager and assigned office staff in disposable local fixtures. It checks four records and eight receipts, denies clinicians, foreign referral links and unassigned office-staff patient links. Temporary fixture role changes are restored before lifecycle tests. They never modify hosted or production identities.

Dedicated patient selection preserves agency-wide manager access and assignment-limited office-staff access. The existing clinical roster remains unchanged. Source patient_management also permits immutable patient creator provenance; that branch is not modeled yet and remains denied. We do not infer creators or broaden office access to the entire agency. Both new database entry points verify current native session, identity, agency, membership and active patient, and lock the office assignment before returning the five-field patient projection. A paging anchor must itself remain visible. The S3 transaction scope also rechecks and locks the active office assignment for create, confirmation, current reads and exact receipt replay. A prior selection is never treated as a lasting capability. This deliberately narrows the earlier synthetic S3 office policy to the currently proven assignment branch. No direct table grants or RLS changes are introduced.

Selected forms remain mounted, hidden and disabled during roster refresh so an uncertain write keeps its original request identity. Nineteen native database tests include both lock orderings for assignment revocation, patient deactivation, membership revocation and native logout. Restore verification exercises both new entry points after database recovery.

Saved referral discovery uses a bounded current-patient list, ordered by stable referral ID. Each page rechecks the current session, membership, patient version and office assignment; each record is checked against its immutable current receipt before the page returns. A cursor must belong to the same currently authorized patient. Pages are current reads, not a multi-page snapshot. The screen opens the existing referral by its exact ID and never creates a replacement to recover an earlier record. Clinical/document/admission operations remain unavailable.
