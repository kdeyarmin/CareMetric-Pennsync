# Independent staging authority client

This client exercises the six named RPCs in `services/authority-store` using independent Supabase Auth. It is an acceptance client, not selected by the production frontend. No existing Base44 login, entity, function, URL, native identity, provider route or integration release control changes.

The source inventory at `0afa0ff9f6846fa355b895f9cfbe142be201dc1f` still contained 444 direct entity calls across 69 entity types and 179 frontend files, 188 function invocation occurrences targeting 148 names, and 282 hosted function entries. Porting this first slice does not port those workflows.

## Contract and use

`createStagingAuthorityClient(config)` accepts the exact loopback test reference/URL (`local-pennsync-authority`, `http://127.0.0.1:54321`), modern publishable key, the staging app ID, one of the four authorized test aliases, and that actor's independently provisioned Supabase UUID. The four source Base44 user IDs are pinned inside the module. Every hosted target is currently refused, including correctly shaped Supabase URLs and caller-supplied approval flags. No dedicated hosted project has been approved and verified yet. Enabling one requires a reviewed source change that pins its exact reference; a format check or exclusion list cannot establish that a target is authorized to receive passwords.

`signIn(password)` verifies the returned identity twice using the Auth sign-in and current-user endpoints. Tokens stay in memory inside the client. No tokens, passwords, refresh credentials, raw provider errors, storage entries or arbitrary SDK handles are returned. `rpc(name, parameters)` only supports context, memberships, patient roster/detail, assignment change and clinician-membership revoke. It validates exact response fields, actor/agency binding, versions and mutation receipts. The database independently authorizes every request. Client checks do not confer privileges or verify a JWT signature.

`invalidate()` immediately cancels pending operations and discards local access. It is a local fence, not a promise of server revocation; use `signOut()` or the next `signIn()` to clean an established native session. Each valid password grant is kept privately in memory as soon as it arrives, before the independent current-user check. A canceled, failed or timed-out login revokes only its own known candidate with the supported `logout?scope=local` endpoint. A replacement login first cleans known old sessions; an old attempt cannot revoke the replacement. A late grant that is actually delivered after cancellation is inspected within a bounded body-read deadline solely for cleanup, and cannot authenticate the client.

`signOut()` clears access immediately and revokes known sessions. Cleanup has its own deadline and survives cancellation of the old login. A failed or timed-out cleanup reports only `AUTHORITY_SESSION_CLEANUP_FAILED`; its known credential stays in this client instance's memory so a later `signOut()` or `signIn()` can retry. There is no global logout, browser admin credential, persistent token storage or guessed session identifier. If Auth created a session but the response/token was never received, or its grant was unreadable or failed expected-identity validation, this client has no supported exact-session credential to revoke it. Closing the client also discards any unresolved in-memory cleanup credential. Those cases require provider-side reconciliation or expiry; local denial does not prove all native sessions have ended.

Every asynchronous authentication result rechecks the session epoch and timeout before returning. Authentication renewal, MFA, account recovery, production enrollment and full frontend integration are outside this staging client.

The new SQL interface is a staging-only contract with synthetic agencies/patients and no platform-owner exception. It does not silently fall back to Base44 if an operation is unsupported or the target is unavailable. Existing production integration controls remain disabled.

## Review and validation

Run `node --test services/authority-client/*.test.mjs`. Tests cover wrong identities and target projects, account verification, stale session completion, timeout implementations that ignore cancellation, cross-agency or malformed responses, exact mutation receipts, and sanitized failures. Lifecycle tests also model pending verification/logout, failed verification, replacement login, late delivered grants, retryable cleanup, unreadable grant streams and the explicit never-received-grant limitation. These modeled sessions do not establish real Auth behavior. Review reproduced and corrected three earlier defects before release: a final promise-boundary stale response, missing cursor/extra result fields, and successful completion after an ignored timeout.

These transport tests use synthetic responses. The separate local Auth/PostgREST CI suite now also passes with four independently created synthetic users and real signed sessions. Hosted enrollment, an actual browser trace without Base44 execution, full workflow acceptance, customer archive/restore and native device tests remain distinct required evidence. Do not label this client as a completed authority migration.
