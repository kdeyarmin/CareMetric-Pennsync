# Integration state migration history

The first two migrations were applied through Supabase before an interrupted source push. Their exact SQL has now been recovered through read-only `supabase_migrations.schema_migrations` metadata from the existing CM Train project. `001_integration_state.sql` is version `20260916162728` (`pennsync_external_integration_state`); `002_storage_isolation.sql` is version `20260916163258` (`pennsync_external_storage_isolation`). `recovered-history.json` records provenance and SHA-256 values after LF/final-newline normalization. These files restore audit source; adding them to Git does not apply them to the existing database.

The complete source sequence 001–006 can now be replayed into a fresh, isolated environment. It creates `cm_integration_jobs`, `cm_integration_files` with its `owner_kind` and `agency_id` columns, `cm_integration_daily_budget`, seven service-only RPCs, the private bucket and its restrictive browser exclusion. Never replay this sequence against the existing shared CM Train project: 001 deliberately fails on existing resources, and 003 registers an hourly cleanup job. There is no drop/recreate or upsert path for customer resources.

Platform prerequisites are PostgreSQL 17, the Supabase `anon`, `authenticated`, and `service_role` roles, actual Storage catalogs, and `pg_cron`. The installed environment grants `service_role` table access through its historical platform default privileges; 001/004 preserve the original DDL and do not invent missing historical grants. A fresh target must verify its actual ACLs, the required service-only RPC execute grants, browser denials, and storage policy before use. The new local platform has no direct service-role table CRUD; the runtime uses only the named definer RPCs, so this stricter default is preserved rather than granting unnecessary table access. Configure cron only in an isolated rehearsal until its activation is intentionally approved. Do not infer a complete data/file restore or a new hosted deployment from passing schema tests.

`../tests/installed-definition-metadata.json` contains scoped catalog readback from 2026-09-18: columns, defaults, constraints, indexes, function definitions and grants, RLS flags, bucket configuration, restrictive policy, and the one retention schedule. It contains no application rows, object bytes or secrets. The fresh PostgreSQL suite compares the replayed definitions to this evidence, exercises real transactions/concurrency, and proves unrelated synthetic data stays intact. Its Storage/cron catalog doubles are explicitly local; they do not prove Storage HTTP behavior or cron-worker execution. See `../tests/README.md` for reproducible commands and limits.

Recovery readback confirmed empty tables, RLS, revoked browser access, exact RPC identities and a private bucket. No customer files or clinical records were copied.

003_result_retention.sql records bounded cleanup of expired ciphertext. Its rollback-only hosted test preserved unexpired results, cleared expired bytes and retained completed idempotency evidence. Browser roles cannot invoke cleanup. The named hourly job was registered/read back active. Logical 24-hour expiry is immediate; physical clearing can lag the schedule or a backlog exceeding 1000 rows per run.

004_preexecution_retry.sql adds an attempt counter and a server-only daily budget. Only a job marked failed before provider execution can be reclaimed under the actor lock. A new claim invalidates the previous owner; at most three attempts are allowed and safe retries count against the daily budget. Pending, uncertain, completed and expired successful jobs remain fenced.

The first hosted rollback-only test exposed a missing p_ prefix in the insert argument. That installed function was corrected immediately while the service remained paused, then the complete test transaction passed. The current 004 file has the correct argument; 005 records the targeted repair and is a no-op for an already-correct fresh installation.

006_record_owned_files.sql adds `owner_kind` and `agency_id` to `cm_integration_files`, with a CHECK pairing them, so an object can be owned by the caller who uploaded it or by a record whose readers a contract decides. It replaces `cm_integration_file_get`, which now matches `owner_kind = 'subject'` and so no longer returns a record-owned row to its uploader, and adds `cm_integration_file_get_authorized` and `cm_integration_file_record_owned`. Both new functions are revoked from `public`, `anon` and `authenticated` and granted to `service_role` alone, like the five before them. `owner_kind` defaults to `'subject'`, so every row an earlier migration's path writes keeps the behaviour it had. This file was written here rather than recovered from the hosted catalog, so it has no `recovered-history.json` entry and should not be given one.

Passing hosted cases: original-job reuse, stale-claim rejection, bounded retry, daily quota, non-replay of uncertain outcomes, completed-result preservation and restricted grants. Synthetic data was rolled back; job/file/budget row counts were zero. This is not a concurrent multi-client performance test or proof of an authenticated PennSync employee round trip.

007_provider_credential.sql adds the owned successor to Base44's `IntegrationSecret` row: `cm_integration_credential`, one active version per (app, provider) by partial unique index, with the provider API key held as the runtime's AEAD blob and the non-secret resource ids in cleartext columns. Three definer RPCs granted to `service_role` alone are the only way in — the table has forced RLS and no policy. `cm_integration_credential_active` carries the sealed key and `cm_integration_credential_status` does not, as two functions rather than one with a flag, because the projection is the control. Rotation appends a version, retires the previous one under its lock, and deactivation is one-way: the trigger refuses every delete, every edit to anything but `is_active`, and `false -> true`. Forward-only like 005 and 006; it drops nothing. Its refusals are proved against a real cluster in `../tests/postgres-bootstrap.test.mjs` (the edit, delete and reactivation guards, the two-connection rotation, and the browser and service-role denials) rather than asserted from the SQL text. Applying it is an operator step and nothing in this repository has applied it anywhere.

008_telecom_operations.sql lets `SendFax` and `SendSms` be RESERVED — not released. Every operation is reserved in `cm_integration_jobs` before its provider runs, which is what makes a send idempotent and bounds the daily budget, and 006 recorded that the operation list lives in two places: the table's CHECK and a second copy inside `cm_integration_reserve`'s own body. So this replaces the constraint by name and PATCHES the function from its installed definition, refusing if the expected list is absent and doing nothing when it is already extended. Reserving is not sending: whether a fax or a text leaves the service is decided by `INTEGRATIONS_TELECOM_RELEASE`, which is unset, and by a provider credential, which does not exist; both operations are also in `BROWSER_FORBIDDEN_OPERATIONS`, so no browser caller may name either whatever the allowlist says. The behaviour is proved by the existing real-cluster case that reads the names out of the constraint and drives the real reserve function for each, so nothing retypes the list. Forward-only, like 005 through 007; it drops no data. Applying it is an operator step and nothing in this repository has applied it anywhere.
