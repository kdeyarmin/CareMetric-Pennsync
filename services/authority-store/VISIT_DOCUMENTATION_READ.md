# Current-authority synthetic Visit documentation

This additive slice reads one existing immutable S4 Visit by ID using the caller's **current** independent staging authority. It does not require that caller to have created the Visit or possess its request ID. The existing S4 own-request recovery interface remains unchanged. This is a finite synthetic documentation projection, not a patient chart, history/list API, SmartNote workflow migration, provider integration or customer-data transfer.

`public.pennsync_staging_visit_documentation(p_app_id text, p_agency_id text, p_visit_id uuid)` is a POST-only, volatile JSON RPC. It is fixed to staging namespace `6a9881683dc68a0bd54f1ef7`. The public wrapper is SECURITY INVOKER; its private entry is SECURITY DEFINER with an empty search path and the existing verified migration-owner requirement. Anonymous and service-role execution is denied. No public table or direct private table API is added.

The result has the existing authority contract, app ID, native Auth UUID, `staging: true`, `synthetic: true`, full current context, `purpose: documentation`, and exactly two purpose-specific objects:

- `visit`: `id`, `patient_id`, `visit_date`, `visit_type`, `status`, `nurse_notes`, `raw_transcription`, `vital_signs`, `documentation_source`, `grounding_pending`, `emr_handoff_status`, `emr_handoff_history`, `updated_date`.
- `scope`: `agency_id`, `membership_id`, `membership_version`, `tenant_role`, `patient_id`, `access_basis`, `assignment_id`, `assignment_version`.

The server copies these 13 Visit fields exactly from the validated immutable S4 artifacts. S4 has no visit-time field and stores no populated review acknowledgment, so neither is manufactured or returned. No author email, patient name, request ID, history/conversion/compliance payload or provider field is disclosed. The complete JSON response is bounded to 2,500,000 UTF-8 bytes; overflow fails without truncation or an audit row. The strict client uses this method-specific cap while retaining 1 MiB for other methods. Existing wrappers receive their unchanged purpose-bound response through the independent staging adapter. After the strict client verifies the canonical server UUID, this adapter preserves the captured caller's equivalent UUID spelling for the wrapper's exact ID comparison; all other values remain unchanged. A different server UUID is rejected before adaptation, and Base44's existing opaque-ID comparisons are not relaxed.

Only current `agency_admin` and assigned `clinician` roles are supported. Patient status must currently be active and synthetic. Administrators receive `agency_wide` scope with null assignment fields. Clinicians receive `care_team_assignment` scope with the persisted assignment UUID and current assignment version. Manager, office staff, owner exceptions, patient-creator exceptions and other broader source behaviors are not introduced by this slice.

## Authorization and disclosure transaction

The entry takes the existing shared application transaction lock, verifies current signed-session claims against native user/session rows and the immutable identity map, then locks the active agency and current membership. It resolves the patient from the stored Visit, locks the active patient and (for clinicians) the active assignment, and locks the exact Visit and creator receipt. Existing `s4_artifacts` verifies all four immutable artifacts against the stored receipt digest. This integrity lookup is bound to the actual creator, but authorization is bound to the current reader. Receipt/patient/member version snapshots from creation do not replace current authority checks.

An immutable private `visit_disclosure_audit` row must be inserted before a response is returned. It contains only opaque actor, agency, membership, patient, Visit and assignment identifiers, current versions/role/access basis, purpose and server time. It contains no note text, email, token or source response. The table has forced RLS, no allowing policy, and no browser/service CRUD grants. An insertion failure raises fixed `PT503 / PENNSYNC_VISIT_AUDIT_UNAVAILABLE`; no document is returned. Read-only transactions cannot satisfy the mandatory write. A committed audit proves an authorized response was produced, not that a person received or viewed it; delivery can still fail after commit. Repeating a successful read can produce another disclosure row.

Normal authority mutations take the matching exclusive application lock. Native user/session, patient and assignment row locks also fence direct changes for the duration of the read. The native tests observe actual PostgreSQL waits in both orderings: a committed revocation denies the blocked read; a read that acquired authority first finishes before revocation can commit, and every later read is denied. A response already delivered cannot be recalled by later revocation.

## Stable synthetic assignment provenance

The migration appends a server-generated UUID `assignment.id`, unique within the app, without changing the existing composite primary key or mutation response format. Existing synthetic assignments obtain this ID once. This is an independent synthetic identity; it is not represented as an imported Base44 assignment ID. Update/delete triggers prevent rebinding the ID or its app/agency/patient/membership scope and prevent deletion. Supported revoke/regrant changes preserve the ID while updating status/version and normal mutation metadata.

The disclosure table deliberately has no inbound Patient FK, preserving the existing importer's exact foreign-key guard and reversible synthetic Patient import boundary. Its immutable opaque provenance is not a patient deletion API. No source records, hosted data, native identities, release controls or deployed migrations are changed merely by adding this code.

## Verification

The dedicated workflow invokes `node --test services/authority-store/tests/visit-documentation-postgres.test.mjs` with an explicit literal-loopback `/postgres` administrator URL. The harness requires pre-existing test roles, executes no cluster role DDL, and creates/drops only its own random database after recording successful creation. It does not start or stop a PostgreSQL server.

Eighteen native PostgreSQL cases cover exact cross-author reads, role/tenant/unassigned/missing denials, current versions, unchanged own-receipt denial, assignment provenance/regrant, audit failure withholding, artifact corruption, exact Unicode bytes over 1 MiB, oversized privileged-corruption refusal, helper/table/RLS boundaries, membership/logout/patient/assignment revocation in both lock orderings, and read-only transaction denial. The oversized case deliberately removes a storage guard only in its disposable test database; no legal S4 write is claimed to create that corrupted state. Existing authority/S3/S4/import suites and full schema restore are separate regression evidence.

`tests/http-authority.test.mjs` adds real local signed-session, strict-client cross-author reads, exact persisted audit rows, anonymous/foreign/unassigned denials and a scoped local audit-failure injection. Existing assignment/membership revocation and actual Auth logout scenarios also deny documentation reads with the still-signed token. It creates no additional Auth users or mail and uses only the already-owned disposable local stack. Actual Auth/PostgREST acceptance requires the dedicated Docker CI run; native SQL tests alone do not prove gateway signature verification or HTTP serialization.
