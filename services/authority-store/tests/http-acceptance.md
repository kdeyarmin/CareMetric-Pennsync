# Disposable local Auth + PostgREST acceptance

This suite tests the existing staging client and authority migration through actual Supabase Auth, signed access tokens, the API gateway and PostgREST. It does not use the local SQL Auth stubs in `bootstrap.sql` or `fixtures.sql`. It is not proof of hosted enrollment, verified production identity mapping, a full clinical data migration, native apps, or a production cutover. External release controls remain unchanged.

Run on an isolated disposable Linux runner with Docker, Node 24.18.0, pnpm 11.9.0 and Supabase CLI 2.109.1. Extract both `supabase` and its adjacent `supabase-go` delegate from the official CLI archive; the version command alone does not prove delegated commands can run. The local CLI exposes container ports on all interfaces: use an isolated runner or appropriately firewalled development host. Test requests themselves permit only `http://127.0.0.1:54321`. No hosted credentials or repository secrets are required. The parent CI job pins the official CLI download and SHA-256. `PENNSYNC_SUPABASE_CLI` may point to that local executable; otherwise it must be on PATH.

From the repository root:

```sh
pnpm --dir services/authority-store install --ignore-workspace --frozen-lockfile
node --test services/authority-store/tests/http-boundary.test.mjs
node services/authority-store/tests/http-local-stack.mjs start
node --test services/authority-store/tests/http-authority.test.mjs
node services/authority-store/tests/http-local-stack.mjs stop
```

Always run the final scoped `stop` step, including on failure. It uses the documented `--project-id local-pennsync-authority --no-backup` to remove only this harness's disposable containers/data volumes. It requires a local ownership marker in this checkout and does nothing if that marker is absent. The effective Docker context is resolved first; only a local Unix socket or Windows named pipe is allowed. That endpoint is pinned for every lifecycle child and bound to the ownership marker. A changed endpoint makes cleanup fail closed. Startup refuses existing matching containers/volumes, occupied local ports, a previous marker or linked-project metadata. It never adopts an existing database or calls a hosted operation. There is no `db reset`, `db push`, link, deploy or `stop --all` operation.

The CLI wrapper captures start/status/stop output because it can contain API keys. Neither child output, keys, passwords, tokens, Auth response bodies nor database errors are printed. It accepts current CLI `PUBLISHABLE_KEY` and `SECRET_KEY` fields and refuses legacy client API keys. The modern secret key is confined to the local fixture runner's Admin API calls; the authority client receives only the publishable key. A legacy server JWT from local status is used only as a negative RPC test. No credentials are persisted in this harness's output, files or artifacts. CLI-managed disposable Docker volumes have their normal local service configuration.

The CLI-generated config lives at `services/authority-store/supabase/config.toml`. It runs PostgreSQL 17, Auth, PostgREST, gateway, real local Storage and a local email sink; other product services are disabled. Storage uses its own disposable local file volume for the separate integration restoration smoke. The API exposes `public` only. Public signup, anonymous signup, external SMTP, SMS and OAuth providers are disabled. In CLI 2.109.1, `[auth.email].enable_signup = true` enables the email/password provider; the separate `[auth].enable_signup = false` disables public account creation. A real HTTP negative check proves public signup is rejected, the user count stays four, and the local Mailpit sink receives zero emails. The Admin API auto-confirms four local synthetic users with the fixed staging alias names solely to satisfy the existing client contract; no invitations or messages are sent. Their Auth UUIDs are generated by the real Auth service. The fixture SQL writes only the six independent staging authority tables; it never writes `auth.users`, `auth.sessions` or other products' tables. Synthetic provenance hashes are explicitly local fixtures, not claimed verification evidence from Base44.

Eighteen HTTP scenarios cover public signup rejection without an extra user or email; real login/native session creation; anonymous and tampered JWT rejection; privileged token rejection; immutable legacy identity/context binding; two agency isolation; assigned and empty rosters; patient reads; bounded pagination; absence of private/direct table endpoints; untrusted metadata; admin-only grants; idempotency and optimistic versions; assignment and membership revocation; actual Auth logout followed by rejection of the still-unexpired signed token; re-login; and no requests to Base44 or any nonlocal origin. The S4-create subset additionally verifies atomic artifact creation, exact read/retry payloads, foreign/empty-clinician denial, rejection of unsupported findings, assignment/membership revocation, and native logout followed by receipt recovery after re-login. The S3 manual existing-patient subset verifies create/confirm/read, exact retries and stale conflicts, intake-role/tenant denials, native logout/re-login, and trusted membership revocation. Its temporary admin-b revocation is restored under the app lock in a finally block, only to the asserted owned synthetic baseline, so later independent suites remain unaffected. These are not complete S3/S4 or UI acceptance. Three separate process-level boundary tests prove remote endpoint refusal before lifecycle execution, changed-daemon cleanup refusal, and unowned cleanup doing nothing. The dedicated HTTP test fails, rather than skips, if the local stack is unavailable. Each scenario aborts the dependent sequence on failure, preventing invalid tokens or missing setup from producing misleading later results. The final scenario also checks the local mail sink remains empty. Prior PGlite and native PostgreSQL concurrency suites remain separate evidence.
