# Nightly outcome workflow restoration audit — 2026-09-06

## Result

The legacy 06:00 UTC automation called `computeOutcomeMeasures` with an empty
payload. That call could never satisfy the hardened writer's mandatory tenant,
reporting-window, and idempotency gates. The schedule now belongs to
`dispatchNightlyOutcomeMeasures`, a dedicated scheduler-facing function. Its
native `base44/workflows/Nightly Outcome Measure Computation.jsonc` definition
uses `args: {}` and is the sole schedule authority; the duplicate legacy
function automation config is intentionally absent. The dispatcher remains
runtime-inactive until the remaining hosted evidence is complete.

The one-agency writer no longer owns an automation. It can be reached only with
the internal scheduler header or a short-lived HMAC proof generated by the
dispatcher for one exact agency, daily window, benchmark value, and idempotency
key. Both functions default to HTTP 503 unless
`OUTCOME_PIPELINE_RELEASE=enabled-v1` is explicitly configured in the target
environment.

## Scheduler policy

| Property | Exact behavior |
|---|---|
| Schedule | Daily at 06:00 UTC |
| Window | The previous completed UTC calendar day |
| Period type | `daily` |
| Tenant selection | Exact, unique `Agency.id` rows whose status is `active` or `trial` |
| Idempotency key | `nightly-outcome-daily:YYYY-MM-DD`; the writer additionally hashes the agency, window, calculation version, benchmark, and key |
| Dispatch authority | Built-in administrator automation creator or `x-internal-secret`; a deactivated administrator is rejected |
| Worker authority | `x-internal-secret` or a 15-minute HMAC capability bound to every scope-controlling field |
| Bounds | At most 999 rows per status query, 100 verified agencies per tick, and two worker invocation attempts per agency |
| Failure result | Non-PHI counts only; any agency failure makes the dispatcher return HTTP 502 |

The dispatcher refuses caller-selected scope. It first verifies the complete
active/trial agency set, then re-reads each exact agency immediately before
signing and invoking the worker. Query leakage, duplicate ids, status drift,
oversized agency sets, malformed worker responses, and partial failures all fail
closed. A bounded retry reuses the same signed request and therefore the same
writer idempotency key.

## Existing writer and schema gates preserved

`computeOutcomeMeasures` still:

- requires one exact `agency_id`, ordered ISO dates, an explicit supported
  `period_type`, and a 16–128 character idempotency key;
- verifies the exact Agency before service-role clinical reads;
- filters and revalidates every OASIS, Patient, metric, KPI, and run row against
  the requested tenant;
- keeps derived metric/KPI generations append-only;
- publishes a generation only through one full-preimage
  `OutcomeComputationRun.updateMany` transition with `$set`, `$inc`, exact
  `success/updated/has_more` checks, and exact readback;
- hashes the result summary and every derived row, reconciles staged row counts,
  and rejects multiple live or published runs for a logical window; and
- retains its bounded expired-lease reconciliation and idempotent replay path.

No `OutcomeComputationRun`, `PatientOutcomeMetric`, or `AgencyKPI` schema change
was needed for the dispatcher. All three remain service-role-only. The
publication-aware `getPublishedOutcomeMeasures` broker remains the only planned
browser read path; direct browser entity reads and browser recomputation remain
disabled.

## Why the runtime remains inactive

Repository tests cannot establish the datastore guarantees needed to release
this clinical rollup. Before setting `OUTCOME_PIPELINE_RELEASE=enabled-v1`,
staging must prove:

1. full-preimage `updateMany` with `$exists: false`, `$set`, and `$inc` is atomic
   and reports reliable counts under concurrent requests;
2. distinct `OutcomeComputationRun` contenders cannot both become published, or
   a datastore-enforced single-winner publication mechanism is added;
3. the offset-paginated OASIS source remains stable for a complete run, or the
   writer gains a pinned snapshot/checkpoint mechanism;
4. representative existing OASIS rows have audited `agency_id`, response-schema,
   definition, instrument, and clinician-origin provenance; and
5. direct and scheduled two-agency positive, cross-tenant, replay, status-change,
   and concurrency tests pass against the isolated staging app.

Until those gates pass, source deployment is safe but activation is not. No
hosted app, workflow, schema, data, secret, or production resource was changed
as part of this outcome-only implementation.
