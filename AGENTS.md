# AGENTS.md

Instructions for Codex cloud and other AI coding agents working in this repository.

## Cursor Cloud specific instructions

- The VM's default `node` (`/exec-daemon/node`) is v22 and takes PATH precedence, but this repo requires Node `>=24.18.0`. Node 24.18.0 is installed via nvm and prepended to `PATH` in `~/.bashrc`, so a normal interactive shell already resolves the correct node. If a command reports the wrong version, run `export PATH="$HOME/.nvm/versions/node/v24.18.0/bin:$PATH"` (or `nvm use 24.18.0`) first. The startup update script also runs `nvm use 24.18.0` before `pnpm install`.
- Frontend-only SPA: `pnpm run dev` serves Vite on `http://localhost:5173`. There is no local backend; `[base44] Proxy not enabled` is expected/harmless.
- Base44 config comes from `VITE_BASE44_APP_ID` and `VITE_BASE44_BACKEND_URL`, provided as Cursor secrets (Vite reads them at dev-server startup, so restart `pnpm run dev` after they change). When they are set, the app root renders the real branded "Welcome to PennSync" login screen and the sign-in form POSTs to the hosted `base44.app` backend end-to-end; `403 "You must be logged in"` console errors before login are expected. Full authenticated patient/clinical flows additionally require valid login credentials, which are not present by default.
- When the config secrets are absent, authenticated routes redirect to `/login` and render blank. To verify rendering without config, use `/signer` (renders the signing-unavailable state) or `/join` (renders an "Invalid Visit Link" card). Public signer and provider-follow-up capabilities are quarantined: their pages do not call the backend, and their token URL parameters are removed before the React app imports.
- Authenticated login/write flows work end-to-end when valid login credentials exist as secrets (e.g. `PENNSYNC_TEST_EMAIL` / `PENNSYNC_TEST_PASSWORD`): sign-in POSTs to `/api/apps/<appId>/auth/login`, and profile writes (`base44.auth.updateMe`, i.e. `PUT /api/apps/<appId>/entities/User/me`) persist. Form fields backed by `base44.auth.me()` (react-query) briefly show empty/grey placeholder text on reload before the real value loads — wait a few seconds before judging persistence.
- Standard commands (install/dev/build/lint/test/typecheck) are in `package.json` and the table below; do not duplicate them elsewhere.

## Project shape

PennSync (package `base44-app`) is a Vite + React 19 SPA with two selectable backends.

On the default path the Base44 platform (auth, data entities, and the Deno functions under `base44/functions/`) is a hosted remote service. Those Deno functions are not runnable from this repo because there is no `deno.json` or local runner; `src/functions/*` are thin client wrappers that call the remote backend.

The product is migrating off Base44. `VITE_PENNSYNC_BACKEND=independent-staging` builds the same app against Supabase Auth and the owned authority store in `services/authority-store`, through `services/authority-client`. That path is synthetic staging only: four fixed test accounts, names-only patients, and unsupported operations fail closed with no Base44 fallback. Two Railway services support it — `services/integration-runtime` (deployed, paused) and `services/pennsync-api` (source only, not deployed).

Before changing anything in the migration, read [the transition plan](docs/BASE44_TO_RAILWAY_TRANSITION_PLAN_2026-09-19.md) and [the exit decisions](docs/BASE44_EXIT_DECISIONS_2026-09-19.md). A `broker` disposition is checked against the entity's schema under D2's ceiling — no PHI, no authority decision. It is refused outright unless the schema's own `rls` block plainly permits a read (`false` means no client may touch the rows at all, which a generic family would invert; a condition is an authority decision the family cannot evaluate), and it is served read-only unless that block plainly permits every write — only 3 of 31 entities survive this, and none is writable. It is also refused for a table that reaches tenancy through a clinical entity, names a clinical subject, carries a credential (a `code` counts when the row also has an expiry or verification marker) or can hold a file; an exemption is enumerated per field in the manifest's `broker_ceiling` block with a reason, and a stale one fails. Adding a carried entity whose schema names no agency requires a kind in `tools-tenant-decision.json`, and `agency` is the default: `global` is re-checked against the schema and refused if the table carries an actor column, references a carried entity or can hold a file. Adding a backend function, entity schema, workflow or Core integration requires a disposition in `tools-transition-disposition.json`; `broker` on a *function* is checked against the entities its module actually touches (through `entities.Name`, destructuring **and** namespace aliasing) and is refused if it reaches anything the broker family does not serve, indexes the namespace with a computed key, or touches no entity at all — the family serves entities, so a capability using none cannot be replaced by it; a function whose module can do no work (no import, await, network, environment or Base44 client, and no request read beyond the method) cannot be `port`, `broker` or `hub`, so pausing an endpoint means moving it to `preserved_paused` or `retire` in the same change. The same holds for a handler **paused at source** — a module-level flag pinned `false` whose guard returns a refusal. That module usually still imports and awaits, so the inert check cannot see it, and nine such capabilities sat in the port queue as writable work until they were measured. Switching a capability off means changing its disposition in the same change. The port queue's blocker categories are measured from each module AND from the dispositions of the entities it reads, never inferred from the feature: a handler reading an entity dispositioned `retire`, `hub` or `preserved_paused` waits on a decision about that use rather than on a schema, and one reading a carried entity with no policy (`User`) waits on how that entity may be read — D14 left it deliberately unreachable. Only a `records_schema` verdict is refined this way;  a handler that only calls a Core integration waits on the runtime rather than the record store, and one that touches an uploaded file waits on the file layer, because the shared SSRF allowlist names Base44's own storage host. Retiring an *entity* additionally needs a retention basis in the manifest's `retention` block — six years in the export archive if its rows hold any identifier, the named system if it only mirrored one, `none` only for operational or synthetic rows — because `retire` decides the target store and never means delete. Adding Base44 coupling to `src/` fails the surface ratchet. Both run in `pnpm test`.

The record store migration (`services/authority-store/supabase/record-migrations/20260919170000_record_store.sql`) is generated, not written: change the entity definitions, the tenant decisions or the generator and re-run `node tools-entity-schema-plan.mjs --write-migration`. A test fails if the committed SQL and the generator disagree. Its tables are owned by `pennsync_records_owner`, which must never hold `SUPERUSER` or `BYPASSRLS` — either one silently voids all 589 policies — and it grants no caller role anything, because an RLS policy runs with the querying role's privileges, so a caller holding a table would also need the helpers that decide who it is.

A per-capability contract (`20260920000000_contract_policy_library.sql` and the ones that follow) is **hand-written**, because a contract exists precisely when a capability's authorization is its own and there is nothing to generate from. Each one is owned by `pennsync_records_owner` and SECURITY DEFINER so the policies bind it, projects named columns rather than returning a row, adds no tenant predicate the policies already enforce, and keeps its authorization in SQL — `services/pennsync-api/record-contracts.mjs` carries none, deliberately. Each needs a test that proves its refusals against the real migration, and any divergence from the Base44 original must be a narrowing and must be recorded. `caller_tenant_role(agency)` exists for contracts only: no policy may ask it, and it is granted to the record owner alone. A create capability's writable field set is extracted the same way and by NAME rather than from a fence, since the originals do not fence it — `WRITE_POLICIES` in `tools-read-purpose-policy.mjs` names the declaration, and `reserved` names the fields the contract decides rather than the caller, so the emitted SQL refuses them explicitly. The one thing a contract may be generated *from* is a block of policy data that already exists in the original: `node tools-read-purpose-policy.mjs --write` evaluates the fenced purpose blocks in the six authorized-read capabilities and emits them as pure functions with no authorization in them at all — thirty-eight field lists that would otherwise be retyped, which is the transcription D12 settled against. The contracts beside them (`20260920060000_contract_patient_read.sql`, `20260920080000_contract_visit_read.sql`, `20260920100000_contract_document_read.sql`, and the write contracts `…120000_contract_patient_create.sql`, `…130000_contract_patient_update.sql`, `…140000_contract_visit_create.sql`) are hand-written as usual and are the only things that decide who may ask. A write contract's role gate is its own and is often NARROWER than D24: `createAuthorizedVisit` admits `agency_admin`, `manager` and `clinician` only, and `…150000_contract_visit_update.sql` requires `clinician` EXACTLY for its three clinical actions, so a `social_worker` who opens a chart under D24 still cannot schedule or document on it — delete either gate and the policies would let them. That last contract is also the first PARTIAL port (D31): `ACTION_INPUT_POLICIES` names which of `updateAuthorizedVisit`'s nine actions this port **serves** and, for each it does not, **why**, and the generator refuses to run if a declared action is neither or both — so an action added upstream fails the build instead of becoming silently unreachable. Its `note_fnv1a` is a byte-exact port of the browser's `hashNoteText` (`src/components/smartNote/emrHandoff.js`), folding UTF-16 CODE UNITS rather than code points, because the browser recomputes it to decide whether an acknowledgement is stale; the test imports the frontend function rather than copying it. `20260920160000_contract_alert.sql` is the first pair whose OWN authorization was the thing D21 and D24 threw out — both originals call `patientBelongsToCaller`, which reads `Patient.assigned_nurses` — so it carries no chart rule at all and lets the `patient_alert` policies answer; its test seeds a stale address to prove the substitution rather than assert it. `20260920170000_contract_note_history.sql` reproduces the Base44 originals' derived keys BYTE FOR BYTE — `to_json(text)` and `JSON.stringify` are proven to agree, and the payload object is emitted in `canonicalJson`'s key order — because `logical_note_key` groups a note's revisions and the read shows only the latest, so a key that disagreed with a carried row's would surface an older revision beside the newer one as current. It stamps THIS store's membership (`pennsync_private.caller_membership`, the record owner's alone) rather than Base44's `AgencyMembership` id. `20260920180000_contract_assignment.sql` is the only port that **re-enables a capability paused at source** (D33), and is allowed to because the pause names three conditions the owned store meets rather than a product judgement: a create-if-absent unique constraint, one transaction spanning membership, agency, chart and assignment, and "the authenticated concurrency matrix" — which is PROVED with two real connections in `record-contract-postgres.test.mjs`, never asserted. That matrix is not a formality: `select … for update` serializes nothing when the row does not exist, so two concurrent grants both reach the insert, and the contract catches `unique_violation` for `chart_assignment_pkey` and `chart_assignment_request_key` **by name** — re-raising anything else — or the loser gets a raw duplicate-key error the HTTP boundary cannot classify. Its `bounded_reason` is a port of the original's `boundedReason` and is proved against it: JavaScript's trim strips the Unicode space separators, `String.prototype.length` counts UTF-16 code units so astral characters count twice, and the control-character class is tested only AFTER trimming because the trim removes the vertical tab and form feed it would otherwise reject. Do not simplify it to `btrim(x) <> '' and length(x) <= 500`. `20260920190000_contract_tenant_context.sql` is the counter-example to the port queue's own bucket names (D34): `listMyTenantMemberships` and `getMyTenantContext` were counted `records_schema` because they touch entities, but the two they touch — `AgencyMembership` and `Agency` — are the AUTHORITY store's native model, so the contract reads `pennsync_private.membership` and nothing in `pennsync_records` was ever the answer. Before adding a contract, check which store already models what the original reads: `pennsync_staging_memberships` and `pennsync_staging_context` already existed and `resolveAuthority` already calls the second on every request, so on the names alone this contract is redundant — it exists because the staging pair projects `pennsync_private.agency.name`, which is constrained `like 'Synthetic %'`, where the real name is `agency_name` on the carried row. Both contracts also delete the originals' double-read-and-compare machinery and their forty-line `validateMemberships`, which are compensations for having no transaction and for an entity any writer could corrupt; the test asserts the CHECK constraints and the generated `membership_key` that replace them, so deleting one fails the suite. `getMyTenantContext` takes its agency from the envelope and has no `agency_id` parameter: the business API's invariant is that every request names its tenant, so the pre-tenant bootstrap stays on the authority store's own RPC rather than an envelope exemption. `20260920200000_contract_membership.sql` is the write half (D35) and the SECOND partial port: five of `manageAgencyMembership`'s six actions, with `provision` refused BY NAME because its own guard reserves it to the platform owner D14 and D22 removed — the same shape as D31's `set_ai_tags`. The same rule keeps an `agency_admin` off the target list: dropping the platform tier without keeping that would have WIDENED the capability, letting one administrator unmake another. `pennsync_private.membership` gains `pending` and `suspended`, and that closes rather than opens because all 27 readers in this store filter `status = 'active'` — a property of the READERS, so re-check it rather than inherit it. `activated_at` carries a default for the reason `granted_at` does. Do NOT check a target against the carried `User.is_active`: reading it means reading under `user_read`, whose predicate admits only ACTIVE memberships, so a suspended colleague's row is invisible and no suspended member could ever be reactivated — the check fires exactly when it must not. Use `identity_map.enabled`, which is authoritative, visible to a definer, and whose revocation its own trigger makes ONE-WAY. `20260920210000_contract_policy_ack.sql` is the THIRD partial port (D36) and carries two rules to reuse. **Tenancy is not ownership**: the policies put a row in the caller's agency, which is not the same as it being theirs, so a contract over a per-person row keeps its own ownership check — the original says in its header that the entity's write RLS is admin-only for exactly this reason. **A comment is not a permission**: that original's header says the `list` action honours `agency_admin`, and its code gates on `u.role === 'admin'` and never reaches the branch, so porting the comment would hand an administrator a capability the code never gave them. Its `list` is refused by name for D31's reason, and no caller-supplied `ip_address` or `device_metadata` is recorded at all — a contract cannot observe a request, and a forgeable field in a compliance record is worse than an absent one. `20260920220000_contract_ai_agreement.sql` is the FIRST port that audits anything (D37): D25's trail had a test suite and no caller until it. A handler audits through `audit.mjs`, but a CONTRACT that must audit atomically calls `contract_activity_append` in SQL — both are SECURITY DEFINER owned by the record owner, and the attestation carries the event's id, so two round trips cannot be one transaction. That is also what replaces the original's four identity rechecks and two full readbacks: in one transaction neither half can exist without the other. Its `blockedActor` is deliberately NOT ported — `pennsync_private.actor` admits an identity only while `enabled and revoked_at is null`, so a revoked person has no caller identity and every helper answers null; the four carried flags it reads are exactly the self-editable labels D23 forbids. And note the contrast with D36: `ai_content_agreement_attestation`'s read policy is `user_id = caller_user_id()`, so tenancy IS ownership and the contract adds no check of its own. Read the policy to tell which case you are in. `20260920230000_contract_time_off.sql` is four capabilities in one file (D38), and they belong together because they are one bug: `submitTimeOffRequest`, `cancelTimeOffRequest`, `reviewTimeOffRequest` and `getApprovedTimeOff` each answer the same authorization question by reading a DIFFERENT self-editable field of the carried `User` row — `is_approved`, `is_manager`, `role`, `account_type` and string comparisons of `agency_name` — and membership answers all of it. `getApprovedTimeOff`'s "collect every user whose `agency_name` matches and filter the requests by their addresses" step DISAPPEARS rather than being reimplemented, because the table's policy is already `agency_id in caller_agencies()`. Two things had to be reproduced exactly and are proved against the original: `totalRequestedDays` (business days, minus half, never below half) and the rejection of an impossible date like `2026-02-31`, which is why the contract parses a text date instead of taking a `date` parameter. Note also that the carried `User` table has NO `full_name` column, so the originals' `user.full_name || user.email` is only ever the address here. And a plpgsql gotcha the tests caught: a `record` variable that is never assigned raises `record "x" is not assigned yet` when a field of it is read — use plain variables for an OPTIONAL lookup. `20260920240000_contract_credential.sql` ports `submitPersonnelCredential` and deliberately NOT its sibling (D39): `reviewPersonnelCredential` is the first WHOLE capability with no performer left — its only gate is `isAdminLike`, i.e. `u.role === 'admin'`, the tier D14 and D22 removed, and approving is all the endpoint does. **Do not add an approve path to that file** until the exit decisions record who may approve a credential; a test asserts the absence and fails if `status` is ever set to `'approved'` or `approved_by`/`approved_at` written to anything but null. It also refuses an unknown key rather than filtering it, because the original's silent `SELF_SERVICE_FIELDS` filter is what keeps `status` out of a caller's reach AND what loses a misspelled `expiration_date` without telling anyone. **D40 then answered that question** and is the standing rule: where a capability's only gate is the built-in `role === 'admin'`, the successor is an `agency_admin` SCOPED TO THEIR OWN AGENCY — the first deliberate WIDENING in the migration, taken by the owner, unblocking five capabilities. When it hands you one, re-read what the platform tier was STRUCTURALLY preventing rather than just what it permitted: `20260920250000_contract_credential_review.sql` had to add a self-approval refusal, because the original's reviewer held no credentials in any agency and an `agency_admin` does. That check is not redundant with the role gate — the role gate is what makes it necessary. Each capability's purposes are its own: a patient list is asked for `contact` or `roster`, one chart is opened for `smart_note_context`, and a purpose from one is refused in the other — where a list and a single read do share a name, as the visit pair does, the single read is the wider projection and a test fails if the list ever widens under it. `platform_owner` is admitted by every purpose in the originals and by none in the emitted SQL — D14 and D22 removed the platform tier — and the generator refuses to render if dropping it would close a purpose. A domain absent from `POLICY_SQL_FILES` is extracted but not emitted, because policy functions nothing can call are dead SQL; a test asserts such a domain's prefixes reach no migration, and none is absent now. A MUTATION capability declares the mirror image and the same tool carries it (D29): `ACTION_POLICIES` names the fenced block, and `updateAuthorizedPatient`'s six workflow actions over twenty-nine fields become `patient_action_known`, `_admits`, `_writes` and `_rank`. Three properties the read policies do not need are enforced at generation: the action field sets must be **disjoint**, because the original merges a batch of actions into ONE write and asserts this only at runtime; no action field may appear in `PROTECTED_PATIENT_FIELDS`, which is read as a check and deliberately not emitted; and an action's fields must NOT carry `id`, the opposite of the rule a read projection follows. `20260920130000_contract_patient_update.sql` builds its `UPDATE` set list from the keys the caller supplied rather than from a column list of its own — a hand-kept list would let a field added to an action validate and then silently not be written. Two narrowings there are D24's rather than the contract's and are recorded in its header: `office_staff` opens no chart, so it can perform no action although the policy admits it for two; and `medical_record_number` moves only for a caller who opens every chart, because a collision check that cannot see every chart is not narrower, it is broken. Eleven entity schemas ask in words for a datastore uniqueness constraint they never got, and D30 carries them: `DECLARED_UNIQUE` in `tools-entity-schema-plan.mjs` enumerates all eleven, the generator re-checks each against its schema and **refuses a claim it finds and the list does not**, and the eight kinded `unique` become a partial index on `(source_app_id, column)` wherever the entity is carried — six of them, since `Message` and `ScheduledFax` have no table. Two are `unproved` (their own descriptions say uniqueness "must still be proved before migration", which is about the existing rows) and one is `conditional` (unique among active rows only); both kinds emit nothing and owe a reason. `medical_record_number` makes no such claim, which is why that field narrows instead of gaining one. `patient_patient_creation_key_unique` is load-bearing for `createAuthorizedPatient`: the contract catches `unique_violation` **for that index by name** and re-raises anything else, so a rename in the generator turns a correct retry answer into a raw database error.

The broker family beside it (`20260919180000_record_brokers.sql`) is generated the same way, by `node tools-record-brokers.mjs --write`, which writes the SQL *and* `services/pennsync-api/brokered-entities.mjs` together — edit neither by hand. It is the only way a caller reaches a record, so three of its properties are load-bearing rather than stylistic: a broker stamps tenancy and refuses a payload naming it, the agency is checked against `caller_agencies()` rather than the request, and the family serves only entities dispositioned `broker` (the generator refuses to run while any of them fails D16's ceiling). Adding an entity means changing its disposition, not the SQL; a `shared` entity is refused outright because the family does not model the platform flag that publishes a row to every agency. The family serves three entities, all read-only, and that is not a stub: D22 taught the ceiling to read each schema's own `rls` block, and 28 of the 31 it used to serve declare an authority decision the generic family cannot evaluate. Restoring one takes a schema that permits the read, not an edit to the allowlist.

`Document` is the one entity with a `binding` tenant path (D27): it has no `agency_id`, so `document_tenant_binding` carries its tenancy and the policies ask that table rather than following `document.patient_id` to a chart — which left a document bound to an agency and no patient invisible to everyone, an agency administrator included. Declared in `BINDING_TENANCY` and re-checked by `applyBindingTenancy` against the schemas, never inferred: "some carried table references me and has an agency" is true of dozens of tables. A claim that does not hold throws rather than falling back to the path it replaced. One consequence to know: a document with no binding is in no tenant and belongs to nobody, so a write creates the binding first.

Four carried entities get a read and an insert policy and **no update or delete policy at all** (D32), because their own descriptions call the ROW immutable or append-only: `ContentScopeBinding`, `DocumentTenantBinding`, `FleetServiceReview` and `PatientNoteHistoryEntry`. The signal is the DESCRIPTION, never the `rls` block — 68 carried entities declare `{create,read,update,delete: false}` there, `Patient` and `Visit` among them, because in Base44 that block means "no client, only a service role" and in this store every path is a service-role path. All twelve entity-level immutability mentions are enumerated in `DECLARED_IMMUTABLE` by kind (`row` or `field`, since eight of them call a FIELD immutable inside a row that is versioned), a `field` claim owes a reason, and a thirteenth fails the run. With no policy for a command PostgreSQL matches no rows rather than raising, so the tests assert zero rows affected; the owner half is proved on real PostgreSQL because PGlite's isolation suite applies the DDL without the role wrapper. Do not add an update policy to any of the four — a correction writes a NEW row.

`User` is the one entity with a `roster` tenant decision (D23): one read policy and no write policy, whose predicate asks `caller_roster_ids()` — the authority store's membership — rather than reading the row's own `agency_id`, `agency_name` or `account_type`, each of which the entity schema describes as a self-editable label that must never authorize. Do not add a write policy to it; the profile-write path is deliberately open and a write policy would settle it by accident. A helper a policy calls must also appear in the owner's `grant execute` list, or the read fails outright with `permission denied for function` rather than returning no rows — a policy expression runs with the querying role's privileges, and inside a broker that role is the record owner.

D24 narrows a chart to its care team on top of tenancy: `caller_opens_every_chart(agency)` is true for an `agency_admin` or `manager`, `caller_assigned_patients(agency)` enumerates the assignments of a `clinician`, `social_worker` or `spiritual_care` worker, and `office_staff` open none. Which tables carry it is **derived** — any entity with tenancy of its own and a top-level `patient_id`, `target_patient_id` or `related_patient_id`, plus `Patient` itself — and the rest inherit it through their reference predicate, because `chartPredicate` is carried in at every hop of `tenantPredicate`. Do not narrow only the root: a reference predicate inlines the target's *tenant* check, so `Patient` alone left fifty-four tables agency-wide. A row whose subject is null stays agency-scoped, because a referral taken before a patient exists is not yet anybody's chart. The chart root's INSERT is the one place the narrowing does not apply (D28): a `patient` row being inserted IS the chart, so its id can never be in `caller_assigned_patients`, and the predicate there refuses every role that does not already open every chart — a clinician could not create a patient at all. Tenancy still applies, and read, update and delete keep the narrowing, so creating a chart does not open it: `insert … returning` is a READ of the new row and a clinician is refused it, which PostgreSQL reports as `new row violates row-level security policy` even though the same insert without `returning` succeeds. Closing that gap means granting the care-team assignment too, which is a write to `pennsync_private` — grant first, then insert, because an assignment naming a patient that does not exist is inert while a chart its creator cannot open is not. `20260920110000_claim_new_chart.sql` is that bridge: `pennsync_private.claim_new_chart(agency)` mints a chart identity and takes the caller's own care-team seat. It takes an agency and **nothing else** — a caller who could name the id would name a chart that already exists, so do not add a parameter for one, and do not add one naming a person either. It has no public wrapper and is granted to `pennsync_records_owner` alone: the only caller is `contract_patient_create`, which claims and inserts **in one transaction**, because the two ownership domains are two schemas in one database and atomicity is available. The grant-first ordering is the failure analysis, not the design. It lives in the record migration directory despite creating `pennsync_private` objects, because it asks `pennsync_records.caller_tenant_role` and every authority migration applies first. The record owner has `usage` on `pennsync_private` and `execute` on that one function, which buys it no table there — but **never** add a blanket `revoke all on all functions in schema pennsync_private` to tidy up what usage exposes: every `pennsync_staging_*` wrapper is an invoker calling an inner function granted to `authenticated`, and nine suites go red. Both halves of D24 are mandatory before porting any capability that authorizes on care-team membership, and the port queue checks for both by looking at the files rather than asserting: delete either and the 36 are blocked again. The other half is `tools-pennsync-assignment-backfill.mjs`, which carries **`PatientCareTeamAssignment`** into `pennsync_private.chart_assignment`. Do **not** source it from `Patient.assigned_nurses`: `listAuthorizedPatients` says in its own header that those emails are not authority, `PatientCareTeamAssignment` is server-owned (`rls` denies every client operation) with a grant/suspend/revoke lifecycle, and its `source` enum already contains `legacy_assigned_nurses` — Base44 migrated those addresses into assignment rows long ago. Reading them again resurrects access somebody revoked, because the address stays on the patient row after the assignment is suspended. Only an `active` assignment carries; resolution is by Base44 user id against `identity_map.base44_user_id`, never by email; the membership must be in the assignment's agency; an assignment already recorded is never re-granted; and a leftover `assigned_nurses` address is reported as a reconciliation finding, never granted. D33's `20260920180000_chart_assignment_lifecycle.sql` is what makes the whole of D24 operable: until it, the only writers of `chart_assignment` were that backfill and `claim_new_chart`, so a clinician could be put on a chart by creating it and taken off it by nothing. It adds a `suspended` status — `caller_assigned_patients` already filters `status = 'active'`, so a suspension closes the chart with **no helper change** while keeping the record that the person was once on it — plus a transition trail and the partial unique index that makes a retry idempotent. A revocation is terminal; putting somebody back is a new grant. `granted_at` carries a DEFAULT and that is load-bearing, not tidy: both pre-existing writers insert an active row without naming it, and with the column merely nullable the coherence check refused every grant they made — the shared fixtures failed on their first insert. The provenance trigger is untouched and still refuses every delete and every change to `(id, app_id, agency_id, patient_id, membership_id)`.

There are **two** care-team tables and they are not interchangeable. `pennsync_private.assignment` is the staging one: it keys to `pennsync_private.patient`, which refuses a real name and refuses `synthetic = false`, and `mutate`, `visible_patient` and the archive import all depend on it. **Never drop its patient foreign key** — it is one of four inbound RESTRICT keys `tools-pennsync-archive-import.mjs` pins by name so that rolling back an imported patient refuses while something clinical still references it; dropping it removes a deletion guard and every import case fails `IMPORT_SCHEMA_UNSAFE`. `pennsync_private.chart_assignment` (`20260920040000_chart_assignment.sql`) is the production one, unkeyed on patient because a chart of record lives in `pennsync_records`, a schema owned by another role.

**Twenty suites are not in `pnpm test`** — twelve postgres-backed, three that need a running local stack, two the integration runtime starts, and four browser ones — so a change here can pass lint, the whole suite, the build, the typecheck gate and all eight gates and still fail CI, which it did three times because the set was guessed at rather than enumerated. `src/testRegistryContract.test.js` now enumerates it for you: it fails if a `services/**/*.test.mjs` runs in neither a `test:*` script nor a workflow, and it fails if anything the ISOLATED authority job runs reaches a package that job does not install — that job does `pnpm --dir services/authority-store install --ignore-workspace` and no root install, so a suite there importing a root tool that imports `json5` dies at load, before an assertion, in under a second. Adding a contract test means adding it to `test:authority-store` in the same change; five drifted before the guard existed. The postgres set: They all need `PENNSYNC_TEST_PG_URL`, and `restore-postgres` additionally needs `PENNSYNC_TEST_PG_BIN` plus real `pg_dump`/`pg_restore`:

```
services/authority-store/tests/{postgres,s4-postgres,visit-documentation-postgres,
  patient-context-postgres,visits-schedule-postgres,referral-patients-postgres,
  referral-list-postgres,s3-postgres,restore-postgres,
  record-contract-postgres}.test.mjs
services/integration-runtime/tests/postgres-bootstrap.test.mjs
tools-pennsync-archive-import.postgres.test.mjs
```

Run **all of them** when touching that schema; `.github/workflows/pennsync-authority.yml` is the list of record. To get a cluster here: `initdb` refuses to run as root, so run it as the `postgres` user with a data directory under `/var/tmp`, listen on `127.0.0.1:5432`, and create the three roles the harnesses require and never create — `anon`, `authenticated`, `service_role`. Two ratchets fail closed on a new table and are meant to: `restore-schema-fixture.mjs` pins every covered table and column, and `record-store-migration.test.mjs` carries a PGlite equivalent of the archive import's inbound-key guard.

The hand-written migrations beside them in that directory exist because a contract's authorization is its own and there is nothing to generate from. Both refuse a database without `caller_tenant_role`, so they apply after the record store; `provision.test.mjs` asserts that order. `20260920010000_activity_audit.sql` is the general activity trail (D25) and the one to reach for when porting a handler that wrote `UserActivity`, `SecurityLog` or `SystemLog` — those are dispositioned `retire`, which decided where their existing rows go and never that the product stops auditing. Write through `services/pennsync-api/audit.mjs`, which every handler is handed as `audit` alongside `integration`, `records` and `contract`. Three of its properties are load-bearing: the table has an insert policy and a read policy and **no update or delete policy at all**, so forced RLS refuses a rewrite from everyone including the record owner — do not add one; the actor is stamped from the caller helpers and a payload naming one is refused; and an oversized `detail` is refused rather than truncated, because a silently truncated audit entry is worse than a refused write. Appending needs only membership, reading needs `agency_admin`. The capability deliberately lives outside `record-contracts.mjs` so that module's "every contract has a handler" invariant stays true — auditing is a facility, not an endpoint. `20260920030000_contract_roster.sql` is the staff roster: its FROM clause is the authority store's membership joined to the carried profile row, so membership decides who is on the roster and the carried row contributes only what the authority store has no column for. It does not project `role`, `account_type`, `agency_id` or `agency_name` from that row under any name, and `is_manager` and `is_approved` are derived from the authoritative tenant role rather than read from the self-editable booleans; personnel detail widens for an `agency_admin` or `manager` and is null, not absent, for everybody else. Reach it through `contract('listAgencyRoster' | 'getAgencyRosterMember', …)` when porting any of the 35 capabilities that read `User`; each contract declares its own refusal codes, so a code one contract cannot raise never crosses back from another.

Use pnpm through Corepack. Do not use npm or yarn for installs.

## Running, building, and testing

Standard scripts are in `package.json` and `README.md`. Notable points:

- `pnpm run dev` starts only the Vite dev server (default `http://localhost:5173`) inside the cloud environment.
- `pnpm test` runs the utility/core, schema/contract, security, deduplication, and component/page suites.
- `pnpm run lint` is clean: 0 errors AND 0 warnings. Keep it that way — a new warning is a real finding, not background noise. Coverage includes `src/App.jsx`, `src/main.jsx`, and `src/routes.jsx`.
- `pnpm run typecheck` is an informational baseline in CI (`continue-on-error`); it may report pre-existing errors and is not a gate.
- `pnpm run typecheck:signal` **is** a CI gate (CI + Workflow Quality). It filters the checkJs pass to high-signal defect codes; keep it at 0 findings.
- Accessibility axe runs on PRs/`main` via `.github/workflows/a11y.yml` (`test:a11y` + Playwright public routes). Local: `pnpm run build && pnpm run test:a11y:e2e`.
- Backend/Deno function syntax checks and Base44 inline-parity tests transpile via `tools-transpile-ts.mjs` (esbuild), not the classic `typescript.transpileModule` API — so TypeScript 7+ is supported for `tsc`/typecheck.
- CI uses Node 24.18.0 with pnpm 11.9.0. Use `.nvmrc` / `.node-version` plus Corepack in cloud environments.

## Environment config

`VITE_PENNSYNC_BACKEND` selects the backend. Omitted or `base44` keeps the production path; `independent-staging` requires the `VITE_PENNSYNC_STAGING_*` values documented in `.env.example` and `docs/INDEPENDENT_STAGING_APP.md`, and fails closed before a Base44 client can be constructed if any of them is missing or invalid.

On the Base44 path the frontend reads `VITE_BASE44_APP_ID` and `VITE_BASE44_BACKEND_URL` (consumed in `src/lib/app-params.js`), the optional exact `VITE_BASE44_FUNCTIONS_VERSION`, and the optional `VITE_SUPER_ADMIN_EMAIL` override used by `src/lib/superAdmin.js`. Function-revision URL and storage overrides are scrubbed; floating version aliases are rejected. The Vite dev server boots regardless, but without a valid app id + backend URL the app shows a blocking config state or redirects to `/login` and renders blank because `/login` is served by the hosted backend, not client-side.

App id and backend URL can also be passed via URL params `?app_id=...&server_url=...`, which are persisted to localStorage. Other vars such as `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `HEYGEN_API_KEY`, and `SIGNATURE_HMAC_SECRET` are backend Deno-function secrets and are not used by the local frontend bundle.

## Testing the running app in a browser without backend credentials

- Authenticated routes are gated; without a real backend they redirect to `/login` and may appear blank.
- `/signer` renders a static signing-unavailable state and `/join` renders an "Invalid Visit Link" card with no token. Use these to verify the SPA renders in a browser. Do not treat the quarantined signer or provider-follow-up routes as end-to-end capability tests.
- Console 404s against the backend origin such as "App not found" are expected when `VITE_BASE44_APP_ID` or `VITE_BASE44_BACKEND_URL` points at a non-existent app.
- Core clinical logic (OASIS scoring in `src/components/oasis/`, PDGM grouping in `src/components/pdgm/pdgmGrouper.js`, SmartNote compliance, fax/SMS/voice utils) is pure and covered by the automated test suite.

## Full end-to-end authenticated flows

Logging in and exercising patient/clinical workflows requires a real hosted Base44 app. Set `VITE_BASE44_APP_ID` and `VITE_BASE44_BACKEND_URL` in Codex environment settings and use valid login credentials. These are not present in the default cloud environment.

## Debugging expectations

When asked to debug, do not make a small isolated patch unless the user explicitly asks for one.

Always:

- Inspect the full feature path and related files.
- Identify root causes before editing.
- Create a complete bug inventory first.
- Check for duplicated patterns elsewhere.
- Run lint, typecheck, tests, and build when available.
- Add or update tests when practical.
- Review the final diff for regressions.

## Done means

A task is not complete until:

- All known related bugs have been listed.
- Safe fixes have been implemented.
- Validation commands have been run or clearly explained if unavailable.
- Remaining risks are documented.
