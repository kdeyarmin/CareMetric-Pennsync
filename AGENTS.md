# AGENTS.md

Instructions for Codex cloud and other AI coding agents working in this repository.

## Cursor Cloud specific instructions

- The VM's default `node` (`/exec-daemon/node`) is v22 and takes PATH precedence, but this repo requires Node `>=24.18.0`. Node 24.18.0 is installed via nvm and prepended to `PATH` in `~/.bashrc`, so a normal interactive shell already resolves the correct node. If a command reports the wrong version, run `export PATH="$HOME/.nvm/versions/node/v24.18.0/bin:$PATH"` (or `nvm use 24.18.0`) first. The startup update script also runs `nvm use 24.18.0` before `pnpm install`.
- Frontend-only SPA: `pnpm run dev` serves Vite on `http://localhost:5173`. There is no local backend; `[base44] Proxy not enabled` is expected/harmless.
- Base44 config comes from `VITE_BASE44_APP_ID` and `VITE_BASE44_BACKEND_URL`, provided as Cursor secrets (Vite reads them at dev-server startup, so restart `pnpm run dev` after they change). When they are set, the app root renders the real branded "Welcome to PennSync" login screen and the sign-in form POSTs to the hosted `base44.app` backend end-to-end; `403 "You must be logged in"` console errors before login are expected. Full authenticated patient/clinical flows additionally require valid login credentials, which are not present by default.
- When the config secrets are absent, authenticated routes redirect to `/login` and render blank. To verify rendering without config, use `/signer` (renders the signing-unavailable state) or `/join` (renders an "Invalid Visit Link" card). Public signer and provider-follow-up capabilities are quarantined: their pages do not call the backend, and their token URL parameters are removed before the React app imports.
- Authenticated login/write flows work end-to-end when valid login credentials exist as secrets (e.g. `PENNSYNC_TEST_EMAIL` / `PENNSYNC_TEST_PASSWORD`): sign-in POSTs to `/api/apps/<appId>/auth/login`, and profile writes (`base44.auth.updateMe`, i.e. `PUT /api/apps/<appId>/entities/User/me`) persist. Form fields backed by `base44.auth.me()` (react-query) briefly show empty/grey placeholder text on reload before the real value loads — wait a few seconds before judging persistence.
- Standard commands (install/dev/build/lint/test/typecheck) are in `package.json` and the table below; do not duplicate them elsewhere.

## Project shape

PennSync (package `base44-app`) is a Vite + React 19 SPA with two selectable backends.

On the default path the Base44 platform (auth, data entities, and the Deno functions under `base44/functions/`) is a hosted remote service. Those Deno functions are not runnable from this repo because there is no `deno.json` or local runner; `src/functions/*` are thin client wrappers that call the remote backend.

The product is migrating off Base44. `VITE_PENNSYNC_BACKEND=independent-staging` builds the same app against Supabase Auth and the owned authority store in `services/authority-store`, through `services/authority-client`. That path is synthetic staging only: four fixed test accounts, names-only patients, and unsupported operations fail closed with no Base44 fallback. Two Railway services support it — `services/integration-runtime` (deployed, paused) and `services/pennsync-api` (source only, not deployed).

Before changing anything in the migration, read [the transition plan](docs/BASE44_TO_RAILWAY_TRANSITION_PLAN_2026-09-19.md) and [the exit decisions](docs/BASE44_EXIT_DECISIONS_2026-09-19.md). A `broker` disposition is checked against the entity's schema under D2's ceiling — no PHI, no authority decision. It is refused outright unless the schema's own `rls` block plainly permits a read (`false` means no client may touch the rows at all, which a generic family would invert; a condition is an authority decision the family cannot evaluate), and it is served read-only unless that block plainly permits every write — only 3 of 31 entities survive this, and none is writable. It is also refused for a table that reaches tenancy through a clinical entity, names a clinical subject, carries a credential (a `code` counts when the row also has an expiry or verification marker) or can hold a file; an exemption is enumerated per field in the manifest's `broker_ceiling` block with a reason, and a stale one fails. Adding a carried entity whose schema names no agency requires a kind in `tools-tenant-decision.json`, and `agency` is the default: `global` is re-checked against the schema and refused if the table carries an actor column, references a carried entity or can hold a file. Adding a backend function, entity schema, workflow or Core integration requires a disposition in `tools-transition-disposition.json`; `broker` on a *function* is checked against the entities its module actually touches (through `entities.Name`, destructuring **and** namespace aliasing) and is refused if it reaches anything the broker family does not serve, indexes the namespace with a computed key, or touches no entity at all — the family serves entities, so a capability using none cannot be replaced by it; a function whose module can do no work (no import, await, network, environment or Base44 client, and no request read beyond the method) cannot be `port`, `broker` or `hub`, so pausing an endpoint means moving it to `preserved_paused` or `retire` in the same change. The same holds for a handler **paused at source**, which comes in TWO shapes and the check knows both (D47): a module-level flag pinned `false` whose guard returns a refusal, and a handler whose FIRST statement is an unconditional `return` with the real body unreachable below it. The second shape hid six capabilities that were dispositioned `port` and counted as writable work until `isRefusingHandler` was added — the same failure the flag check was written to fix, in a shape nobody re-measured, so when a check exists to stop a class of mistake, re-derive the shapes from the tree rather than from the check. That module usually still imports and awaits, so the inert check cannot see it, and nine such capabilities sat in the port queue as writable work until they were measured. Switching a capability off means changing its disposition in the same change. The port queue's blocker categories are measured from each module AND from the dispositions of the entities it reads, never inferred from the feature: a handler reading an entity dispositioned `retire`, `hub` or `preserved_paused` waits on a decision about that use rather than on a schema — unless the manifest's `uncarried_legs` block settles that leg for that capability by name (D84), giving the entities, what serves them instead and a reason of at least twenty characters; an entry is refused, and blocks the census, unless its capability is still a `port` and still reaches every entity it names, so repointing a leg, porting it or retiring the capability each fail until the entry goes with it. A handler WRITING a carried entity waits on whether the store permits that write, which after D82 is not one question: `user` carries an update policy naming `caller_user_id()` and a trigger admitting only `PROFILE_SELF_WRITABLE`, so a write is admitted only where the payload can be read, every column of it is on that allowlist, and the module has a caller at all — a `schedulerAuth` fence means there is none. Both the policies and the allowlist are parsed out of the emitted SQL rather than kept in a second copy here. A `global` reference table is written by migration and never at runtime (D83), so a handler whose purpose is to write one is not a port to schedule. Only a `records_schema` verdict is refined this way; a module that reaches the FILE LAYER and whose record half is otherwise clear reports `files` (D65), because the store is built and the file layer is not — the classifier used to return the store first and its own comment said why, and that reason expired when the store was finished; the refinement fires after the entity checks, because those name a decision nobody made and a decision outranks work that is merely large.   a handler that only calls a Core integration waits on the runtime rather than the record store, and one that touches an uploaded file waits on the file layer, because the shared SSRF allowlist names Base44's own storage host. Retiring an *entity* additionally needs a retention basis in the manifest's `retention` block — six years in the export archive if its rows hold any identifier, the named system if it only mirrored one, `none` only for operational or synthetic rows — because `retire` decides the target store and never means delete. It is a SIGNAL and not a gate, because the apply is an operator action on a machine CI cannot reach and nothing in a pull request could satisfy a gate. It reads the PIN rather than the directory, which is the house defect waiting to happen — a change that added a migration and did not re-pin would report nothing arriving, quietly — so both sides are cross-checked against the files they describe (the head through `fingerprints()`, the base by NAME through `git ls-tree`) and a disagreement REFUSES instead of returning a number. It claims nothing about what a deployment holds; that stays the hosted comparison's half, and merging the two answers is how a prediction gets read as a measurement. **The ledger's own half shipped as D94**: `tools-pennsync-ledger-statements.mjs` records every migration's text in `supabase_migrations.schema_migrations.statements`, inside the migration's transaction beside its `version` and `name`, and every run — including a read-only plan — reports what the rows already there do and do not say. Three things about it are load-bearing rather than stylistic. services/authority-store/tests/{postgres,s4-postgres,visit-documentation-postgres,
```
  patient-context-postgres,visits-schedule-postgres,referral-patients-postgres,

```

Run **all of them** when touching that schema; `.github/workflows/pennsync-authority.yml` is the list of record. To get a cluster here: `initdb` refuses to run as root, so run it as the `postgres` user with a data directory under `/var/tmp`, listen on `127.0.0.1:5432`, and create the three roles the harnesses require and never create — `anon`, `authenticated`, `service_role`. Two ratchets fail closed on a new table and are meant to: `restore-schema-fixture.mjs` pins every covered table and column, and `record-store-migration.test.mjs` carries a PGlite equivalent of the archive import's inbound-key guard.

The hand-written migrations beside them in that directory exist because a contract's authorization is its own and there is nothing to generate from. Both refuse a database without `caller_tenant_role`, so they apply after the record store; `provision.test.mjs` asserts that order. `20260920010000_activity_audit.sql` is the general activity trail (D25) and the one to reach for when porting a handler that wrote `UserActivity`, `SecurityLog` or `SystemLog` — those are dispositioned `retire`, which decided where their existing rows go and never that the product stops auditing. Write through `services/pennsync-api/audit.mjs`, which every handler is handed as `audit` alongside `integration`, `records` and `contract`. Three of its properties are load-bearing: the table has an insert policy and a read policy and **no update or delete policy at all**, so forced RLS refuses a rewrite from everyone including the record owner — do not add one; the actor is stamped from the caller helpers and a payload naming one is refused; and an oversized `detail` is refused rather than truncated, because a silently truncated audit entry is worse than a refused write. Appending needs only membership, reading needs `agency_admin`. Its read is `order by occurred_at desc, id desc`, and the id is there for PAGING — it is a random uuid, so which of two rows sharing a microsecond comes first is a coin flip. A test may assert that the timestamps descend and that a walk is the whole trail exactly once; it may NOT assert which row is at a given index unless the list has one row or the ordered column is distinct by construction. `activity-audit.test.mjs` asserted `entries[0].action` was `step.9` and CI caught it being `step.8` once in nine runs — the assertion, not the contract, was wrong. Every ordered read in the record migrations has a tiebreaker and was re-checked when that fired; the shape to look for is a position assertion over rows a contract wrote in a loop. The capability deliberately lives outside `record-contracts.mjs` so that module's "every contract has a handler" invariant stays true — auditing is a facility, not an endpoint. `20260920030000_contract_roster.sql` is the staff roster: its FROM clause is the authority store's membership joined to the carried profile row, so membership decides who is on the roster and the carried row contributes only what the authority store has no column for. It does not project `role`, `account_type`, `agency_id` or `agency_name` from that row under any name, and `is_manager` and `is_approved` are derived from the authoritative tenant role rather than read from the self-editable booleans; personnel detail widens for an `agency_admin` or `manager` and is null, not absent, for everybody else. Reach it through `contract('listAgencyRoster' | 'getAgencyRosterMember', …)` when porting any of the 35 capabilities that read `User`; each contract declares its own refusal codes, so a code one contract cannot raise never crosses back from another.

## Running, building, and testing

Standard scripts are in `package.json` and `README.md`. Notable points:

- `pnpm run dev` starts only the Vite dev server (default `http://localhost:5173`) inside the cloud environment.
- `pnpm test` runs the utility/core, schema/contract, security, deduplication, and component/page suites.
- `pnpm run lint` is clean: 0 errors AND 0 warnings. Keep it that way — a new warning is a real finding, not background noise. Coverage includes `src/App.jsx`, `src/main.jsx`, and `src/routes.jsx`.
- `pnpm run typecheck` is an informational baseline in CI (`continue-on-error`); it may report pre-existing errors and is not a gate.
- `pnpm run typecheck:signal` **is** a CI gate (CI + Workflow Quality). It filters the checkJs pass to high-signal defect codes; keep it at 0 findings.
- Accessibility axe runs on PRs/`main` via `.github/workflows/a11y.yml` (`test:a11y` + Playwright public routes). Local: `pnpm run build && pnpm run test:a11y:e2e`.
- Backend/Deno function syntax checks and Base44 inline-parity tests transpile via `tools-transpile-ts.mjs` (esbuild), not the classic `typescript.transpileModule` API — so TypeScript 7+ is supported for `tsc`/typecheck.
- CI uses Node 24.18.0 with pnpm 11.9.0. Use `.nvmrc` / `.node-version` plus Corepack in cloud environments.

## Environment config

`VITE_PENNSYNC_BACKEND` selects the backend. Omitted or `base44` keeps the production path; `independent-staging` requires the `VITE_PENNSYNC_STAGING_*` values documented in `.env.example` and `docs/INDEPENDENT_STAGING_APP.md`, and fails closed before a Base44 client can be constructed if any of them is missing or invalid.

On the Base44 path the frontend reads `VITE_BASE44_APP_ID` and `VITE_BASE44_BACKEND_URL` (consumed in `src/lib/app-params.js`), the optional exact `VITE_BASE44_FUNCTIONS_VERSION`, and the optional `VITE_SUPER_ADMIN_EMAIL` override used by `src/lib/superAdmin.js`. Function-revision URL and storage overrides are scrubbed; floating version aliases are rejected. The Vite dev server boots regardless, but without a valid app id + backend URL the app shows a blocking config state or redirects to `/login` and renders blank because `/login` is served by the hosted backend, not client-side.

App id and backend URL can also be passed via URL params `?app_id=...&server_url=...`, which are persisted to localStorage. Other vars such as `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `HEYGEN_API_KEY`, and `SIGNATURE_HMAC_SECRET` are backend Deno-function secrets and are not used by the local frontend bundle.

## Testing the running app in a browser without backend credentials

- Authenticated routes are gated; without a real backend they redirect to `/login` and may appear blank.
- `/signer` renders a static signing-unavailable state and `/join` renders an "Invalid Visit Link" card with no token. Use these to verify the SPA renders in a browser. Do not treat the quarantined signer or provider-follow-up routes as end-to-end capability tests.
- Console 404s against the backend origin such as "App not found" are expected when `VITE_BASE44_APP_ID` or `VITE_BASE44_BACKEND_URL` points at a non-existent app.
- Core clinical logic (OASIS scoring in `src/components/oasis/`, PDGM grouping in `src/components/pdgm/pdgmGrouper.js`, SmartNote compliance, fax/SMS/voice utils) is pure and covered by the automated test suite.

## Full end-to-end authenticated flows

Logging in and exercising patient/clinical workflows requires a real hosted Base44 app. Set `VITE_BASE44_APP_ID` and `VITE_BASE44_BACKEND_URL` in Codex environment settings and use valid login credentials. These are not present in the default cloud environment.

## Debugging expectations

When asked to debug, do not make a small isolated patch unless the user explicitly asks for one.

Always:

- Inspect the full feature path and related files.
- Identify root causes before editing.
- Create a complete bug inventory first.
- Check for duplicated patterns elsewhere.
- Run lint, typecheck, tests, and build when available.
- Add or update tests when practical.
- Review the final diff for regressions.

## Done means

A task is not complete until:

- All known related bugs have been listed.
- Safe fixes have been implemented.
- Validation commands have been run or clearly explained if unavailable.
- Remaining risks are documented.
